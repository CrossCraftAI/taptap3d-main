# M1 — the pitch, specified

`ROADMAP.md` says what M1 is: **the demo script, performed end to end, on a file
we have never seen.** This document is that script turned into something
buildable — the routes, the screens, the contracts and the acceptance tests.

It is subordinate to `DFD.md` and `ARCHITECTURE.md`. Where this document appears
to contradict either, they win and this one is wrong.

---

## 1. The script, as acceptance criteria

Each step is a thing a person does in front of a customer, and each has a check
that either passes or does not. The whole of M1 is done when all six pass in one
sitting, on a file nobody here has opened.

| # | The step | Done when |
|---|---|---|
| 1 | The shell is the landing | `/` lists events as rows with lot and photograph counts, a persistent left navigation, and quick-add reachable without leaving the page |
| 2 | Create an event → an empty editor | Quick-add writes an `event` and lands on `/events/[id]/catalogue` — the editor: a blank A4 sheet on the template's geometry, the layout controls live, the rail put away, and exactly one action on the canvas: import |
| 3 | Import whatever the client brought | `.xlsx`, `.csv`, `.tsv` parse; anything else lands on *paste your text here* with a reason a specialist can read aloud |
| 4 | Field matching, HubSpot-style | Every column is shown with a suggestion, a confidence, and a reason; nothing is applied until a human presses commit |
| 5 | Manual clearance, pins and locks | Any suggestion is overridable; a column can be skipped or kept as a custom field; decisions are recorded as provenance |
| 6 | The template generates a layout | The catalogue preview paginates every lot into a chosen density and renders through the one renderer |

**Step 3 is the largest risk in the business** and is built accordingly: it
degrades, it never throws, and every refusal carries a way forward. That is
already true of `src/lib/import/parse.ts`; M1 is where a screen sits on top of it.

## 2. Routes

```
/                                  the shell — event list, quick-add
/events/[id]                       the event workspace — lots, or the empty state
/events/[id]/import                upload or paste, then match
/events/[id]/lots/[lotId]          one lot — fields, photographs
/events/[id]/catalogue             the preview, paginated, one renderer
/events/[id]/catalogue/pdf         the printed catalogue — the same document
/photographs                       the library — all · unassigned · on a lot

/import                            record: which event the client's file joins
/catalogues                        compose: everything in production
/exports                           publish: the printed catalogue, per event

/api/health                        unchanged, ungated
/api/events/[id]/import/parse      POST  file or text  → ParseResult
/api/events/[id]/import/commit     POST  table+mapping → lots, and an import_run
/api/assets                        POST  many files, lot optional → one verdict each
/api/assets/[hash]                 GET   bytes, org-scoped
/api/lots/[id]/assets              POST  attach · PATCH detach / set plate
/api/actions                       POST  a batch of gestures from one sitting
```

Every object is addressable, every list is a URL, and every action on an object
is a method on that object's own path. That is not tidiness: it is what makes
this system something another one can be pointed at later, and it is the cheapest
time to get it right.

Creating an event and changing the layout parameters are **server actions**, not
routes: both are forms, and a form that works before the bundle loads is worth
having on a demo laptop tethered to a phone. Everything that carries a file or a
payload is a Route Handler.

Server Components read; Route Handlers and actions write. There is no client-side data
fetching library and no store — the matching screen holds one parsed table in
React state for the length of one decision and then posts it.

*Rejected:* persisting the uploaded file server-side so the review screen can
re-read it. The file is the customer's property and frequently their copyright;
holding it turns a thirty-second decision into a retention policy. The parsed
table is small, already in the browser, and the commit sends it back.

## 3. The shell

A left navigation that does not move, a content column, and quick-add reachable
from both. Row-based lists, not cards: a specialist is comparing sixty sales, and
cards make that scrolling.

**What the predecessor got wrong and this does not repeat.** `tap3d` opened on a
project grid with no sense of where anything was, and the editor was a separate
world reached by a link. Here the navigation is present in the editor too — an
event is a place inside the application, not a modal you escape from.

The landing shows, per event: name, date, lot count, photographed count, and how
far the catalogue has got. Those last two are the only progress indicators that
mean anything before a layout exists, and both are already computed by
`listEvents`.

### 3.1 The rail is a flat list of what is built, and it can be put away

The rail is four places — Events · Photographs · Catalogues · Exports — in no
order that means anything. It was seven categories, four of them secretly a
sequence and three of them "not yet" labels, and the owner rejected it: a menu
throws away order, and a roadmap is not navigation. The sequence lives where a
person compares sales — as the *Progress* column of the ledger, with a call to
action that changes with it (`src/lib/workflow.ts`). The whole argument is at
the top of `src/lib/nav.ts`.

**The rail holds places; an object's header holds the actions on it.** A global
*Import* or *PDF export* cannot know which sale a specialist means, so each opens
on the ledger and hands off to the event's own screen. Hoisting one event's
buttons into the global navigation would be choosing for them.

**Nothing inside the rail collapses; the whole rail does.** Four items do not
need a filing system. What a specialist laying out pages needs is the window:
measured on production in a 1440×900 window, the A4 page had 22% of it and the
chrome around it had the rest. So one control — the button in the window's
corner, or Ctrl+\ — puts the entire rail away and brings it back, and every
screen can take the window. The editor arrives with the rail away; everywhere
else it is open until the viewer says otherwise. The choice is remembered in the
viewer's own browser — never a cookie, because it is a per-viewer convenience
with no consequence for anyone else and no business on a request header — and
applied before the first paint, so a remembered choice never flashes. Every
read and write of that storage is wrapped: a private window throws rather than
answering nothing, and a rail that cannot render is worse than one that
forgets. `src/lib/chrome.ts` holds the mechanism; `test/e2e/editor.spec.ts`
holds the number.

## 4. The importer and the matching screen

### 4.1 What arrives

`parseUpload` and `parsePastedText` already return either a `ParsedTable` or an
`UnreadableFile` carrying `reason` and `suggestion`. The screen renders both. An
`UnreadableFile` is **not** an error state: it is the paste box, pre-opened, with
the reason above it.

A workbook's other sheets are named by the parser and offered as a switch. A
title block above the grid is reported as *"ignored 3 rows above the header"*
with the rows visible on demand — silently swallowing them is how a person
discovers at page 40 that lot 1 is missing.

### 4.2 The matching screen

One row per column of the customer's file: their header, sample values, the
suggested field with its confidence, and the reason the suggestion was made.

Three rules, all from `ARCHITECTURE.md` principle 9:

- **Every suggestion is visible, adjustable and reversible.** The dropdown holds
  the nine core fields, *keep as custom*, and *skip*.
- **A proposal is not an edit.** Nothing is written until commit. The screen
  shows the exact lots it is about to create — `applyMapping` is pure, so the
  preview and the commit are the same function, not two that can disagree.
- **What does not fit is kept, not discarded.** An unmatched column defaults to
  *keep as custom* under the customer's own header, never to *skip*. The field
  set is theirs.

### 4.3 Provenance

The commit records an `import_runs` row: source filename, the cleared mapping,
row count, status, and the org. `DFD.md` §4.3 requires the provenance of the
mapping to cross the import → lots boundary; this is that. It does **not** record
the file.

## 5. Photographs and the asset store

Nothing in M0 can hold bytes, and both the photograph path and the predecessor
migration need one. So M1 adds the smallest honest version.

```ts
interface AssetStore {
  put(bytes: Uint8Array, mime: string): Promise<{ hash: string; size: number }>;
  get(hash: string): Promise<Uint8Array | null>;
  has(hash: string): Promise<boolean>;
}
```

- **Content-addressed**, SHA-256, stored at `objects/<hash[0:2]>/<hash>`. Two
  orgs uploading the same photograph share one blob and hold two `assets` rows —
  which is exactly what `schema.ts` already says about `assets_org_hash`.
- **Filesystem-backed**, rooted at `TAPTAP3D_ASSET_ROOT` (`/data/assets` in
  production, `.data/assets` locally), on a Fly volume.
- **Served through `/api/assets/[hash]`**, which resolves the hash *through the
  `assets` table scoped to the acting org*. A store lookup by hash alone would
  let any org fetch any blob by guessing — the predecessor shared its store
  globally and had to reason carefully about what that leaked.

One machine, one volume, deliberately, for as long as the store is a filesystem:
two machines each get their own volume and a photograph uploaded to one 404s on
the other, intermittently. Scaling past one machine is the S3 implementation of
this same interface, and nothing above it changes.

## 6. The catalogue preview

Step 6, and the first appearance of the loop `DFD.md` §4.2 draws.

- **The engine** derives a placement for every lot from `(lots, assets,
  catalogue.params)`. Pure, deterministic, no database, no rendered output read
  back. Density (`perPage`) and image placement are the only parameters at M1.
- **The document** is the tree the engine emits and the only thing the renderer
  reads.
- **The renderer** is one implementation producing the preview today and the PDF
  and the listing later. It emits an HTML document whose **first tag in `<head>`
  is `default-src 'none'`** and which carries **no `sandbox` attribute** — for
  the reason in `ARCHITECTURE.md` principle 8, which cost the predecessor a year
  in Safari.
- **Overrides and pins** are keyed `(lot, field)` and by members respectively,
  never by element id or page number.

M1 renders. It does not yet let a person drag a box — the editing overlay is the
next increment and the reason the renderer is built behind an interface now.

## 7. Migrating the predecessor

`tap3d` holds a database (`fly-db`) and a 71 MB volume (`tap3d_data`, 335 files).
Both come across; neither is trusted to be well-formed.

### 7.1 The mapping

The predecessor has two generations of schema in one database. **Only the second
is migrated** — the first (`tenants`, `events`, `lots`, `media_assets`,
`brand_specs`) is the abandoned tenant-scoped design, and its own source calls
the `lots` table LEGACY and says nothing writes to it.

| `tap3d` | → | `taptap3d` | Note |
|---|---|---|---|
| `tenants` | → | `orgs` | `slug`, `name`. `api_key` is dropped — a credential for an API that no longer exists |
| `projects` | → | `events` | `name`. A project with no tenant joins the default org |
| `project_lots` | → | `lots` | The typed columns collapse into `fields` jsonb under their core keys; `custom_fields` merges in; `sort_order` → `position`; `ref` → `ref` |
| `project_assets` | → | `assets` | `hash`→`content_hash`, `size`→`byte_size`, `mime`→`mime_type`, `filename`→`original_name` |
| `asset_geometry` | → | `assets.geometry` | Joined by hash |
| `lot_assets` | → | `lot_assets` | `asset_hash` resolved to the new `asset_id`; `is_primary` carried, `sort_order`→`position` |
| `layouts`, `layout_versions` | → | `catalogues` | One catalogue per project; `params` from the version's params |
| `lot_field_overrides` | → | `overrides` | `hidden: true` becomes `{"hidden":true}` under `(catalogue, lot, field)` |
| `layout_spreads` | → | `pins` | A spread is an arrangement that must survive re-derivation; its members are the lots on those pages **resolved at migration time**, because a spread is keyed by page and a pin may not be |
| `import_runs` | → | `import_runs` | Carried, because provenance is the point of it |
| `lot_field_proposals` | → | `overrides` with `decided_by = null` | A proposal is not an edit, and a null decider is how `schema.ts` says to express one. `state='rejected'` rows are carried too — a rejection is remembered so the next run does not re-propose it |
| `extraction_cache`, `render_cache`, `verification_cache`, `fixture_results` | | *dropped* | Caches of a renderer that no longer exists. Re-derivable by definition |
| `provenance_log`, `lot_comments` | → | `action_log` | Best-effort, with `session_id` synthesised per source row |

### 7.2 The bytes

`/data/assets/objects` is already content-addressed by the same SHA-256 the new
store uses, so the migration **copies blobs unchanged** and verifies rather than
re-hashes. `derivatives/` and `index/` are not copied: derivatives are
re-derivable and the index is the predecessor's own bookkeeping. `uploads/` is
copied only where a `project_assets` row references it.

### 7.3 How it runs

**Inside Fly, never from a laptop.** The migrator is a script in the image, run
as a one-off against both databases over the private network. Two reasons, and
the second is the real one: a laptop run needs both production credentials
materialised locally, and the predecessor's last round of UAT died precisely
because it depended on a developer's machine being switched on.

It is **idempotent and additive**: every insert is keyed on a natural key
(`orgs.slug`, `(events.org_id, name)`, `(lots.event_id, ref)`,
`(assets.org_id, content_hash)`) and conflicts do nothing. Running it twice
changes nothing the first run did. It never deletes, and it never writes to
`tap3d`.

A dry run prints the counts it would write and exits without opening a
transaction.

`/api/events/[id]/assets`. `/events/[id]/lots/[lotId]` and `/api/actions` are
built — see §8d.

## 8b. Photographs, and why unassigned is a first-class state

Added after M1's first deployment, and it changes the shape of the product rather
than adding a screen to it.

**A photograph does not need a lot.** A photographer shoots a consignment in one
session and hands over four hundred files; the cataloguer works out which lot
each belongs to over the following days, with the objects in front of them. A
system that demands the assignment at the moment of upload makes the easy half of
that job wait for the hard half, and the usual outcome is that the files never
arrive at all and live in a shared drive instead. So `assets` has no lot column —
the link is `lot_assets`, and its absence means *not yet*, never *broken*.

The consequences, each of which is a decision:

- **The whole window is the drop target**, not a rectangle to aim at. A dropped
  **folder** is walked through the entries API, because `DataTransfer.files` is
  empty for a directory and an uploader that silently does nothing looks broken
  rather than incomplete.
- **Uploads go in batches**, so an interrupted run keeps what it stored. The
  store is content-addressed, so resuming costs only the bytes.
- **Every file gets its own verdict.** A batch that refuses wholesale because
  file 303 is a `.DS_Store` is a batch someone has to bisect by hand, mid-shoot.
- **Dimensions are read from the header on the way in** — `src/lib/assets/measure.ts`,
  no image library — because the engine needs a plate's aspect and the only other
  way to learn it is to render something and measure it, which is the dependency
  ARCHITECTURE.md forbids. A file that cannot be measured is still stored.
- **The bytes decide the format, not the file name.** A client's `photo.jpg` that
  is really a PNG is ordinary; trusting the extension stores the wrong aspect.
- **The first photograph on a lot becomes its plate**, unasked. A lot with one
  photograph and no primary renders no plate at all, and *set a primary* is not a
  step anyone should need to know to see their own picture. Detaching the plate
  hands it to the next one.
- **Unassigned is a filter on the landing and a badge on the rail.** It is the
  queue, and a queue nobody can see is a queue nobody works.

Not built: derivatives. The library serves originals lazily, which is honest for
a corpus of this size and will not be for one ten times larger. The store is
content-addressed and ready for a `thumb` derivative; a decoder is the
speculative weight the Dockerfile refuses elsewhere, and it arrives with the
corpus that needs it.

## 8c. The printed catalogue

`DFD.md` §6 calls the print PDF "the deliverable that pays for the software
today". It was deferred at M1's first cut because it meant Chromium and fonts in
the image; it is here now because the demo ended on a screen with no answer to
*"so how do I send this to the printer?"*, which turns a catalogue system back
into a website.

**It is a second consumer of one renderer, not a second renderer.** The route
derives the same document, calls the same `renderCatalogue`, and asks a browser
to print the result. The only thing the preview and the export disagree about is
how a plate's content hash becomes something loadable — a route for the preview,
an inline `data:` URI for the export, which has no origin and no session. That
difference is a leaf, which is what principle 6 is asking for.

**The fonts were the risk, and the first check for them was wrong.** A preview
reads correctly because the *specialist's* machine has a Chinese serif; a server
has none unless one was installed, and the failure is not an error — it is a PDF
of tofu boxes, produced successfully, discovered at the printer's. The first
version enumerated `document.fonts`, which holds only `@font-face` declarations;
this document names system families and declares none, so a machine with every
CJK font installed reported that it had none. The check now measures **paint**:
青 is drawn, so is a private-use codepoint no font carries, and their pixels are
compared. Identical means tofu. The answer travels back on the response as
`x-taptap3d-cjk`.

**Noto Serif CJK HK before TC**, because Hong Kong and Taiwan standardise
different glyph forms for the same characters and the first customers print Hong
Kong catalogues. Both faces are in the image.

Known ceilings, written down rather than discovered:

- Plates are inlined, so one export holds all its photography in memory at once
  — capped at 150 MB of source bytes, past which plates are dropped and counted
  in `x-taptap3d-plates-dropped` rather than the export dying.
- One export at a time. Two concurrent Chromiums on a 2 GB machine is an
  out-of-memory kill that takes the server with it.
- The machine is 2 GB **because of this path** and for no other reason. The
  predecessor set the same number for the same reason.
- The first export after a cold start pays Chromium's first launch. Afterwards it
  is about four seconds for a short sale.

## 8d. The correction loop

`DFD.md` §4.2 calls the loop the product. Until this landed nothing in the
application could correct anything: `overrides`, `pins` and `pin_members` had
one writer, the migration, and the claim that a year of judgement survives a
repagination was a design. It is now a driven test
(`test/e2e/corrections.spec.ts`): three corrections, two density changes, every
correction still standing, then every correction reversed.

**Two reaches, two tables, two gestures.** A typo in a title is wrong in every
catalogue, so fixing it edits the RECORD — `lots.fields`, on the lot page. What
one catalogue should print differently is an OVERRIDE — `(catalogue, lot,
field)`, also on the lot page, under *In the catalogue*. The screen shows the
record, what prints, and a mark where they differ, so a value that is not the
record's can never be mistaken for one (principle 9). An override is `{hidden}`
or `{text}`; `derive()` applies them on every derivation, so a density change
re-applies rather than re-flows. `ref` and the plate are reached by the same
key.

**Who decided, before anyone can sign in.** `overrides.decided_by` makes one
distinction — a human decided, or a machine proposed and nobody confirmed — and
there is no `users` row to name. Writing null "for now" would have destroyed
that distinction the day the vision model proposes anything. So a human decision
is written as the org's **gate identity**: one `users` row per org,
`gate@<slug>.taptap3d.invalid`, made on first use (`src/lib/data/actor.ts`).
It says what is true — a member of the house, before the system could say which
— and dies with `currentOrgId()` when D14 lands. The engine applies rows with a
decider and skips the rest; a proposal stays visible to a person and invisible to
the page.

*Rejected:* a `decided_kind` column, for the reason already in `schema.ts` —
provenance is derived by comparison, not by a flag a restore could make lie.
*Rejected:* reading `{proposal: true}` out of `value`, which is the same flag by
another name.

**A pin is its members.** The list beside the preview selects LOTS, never slots;
the form posts lot ids and nothing about pages. The page number beside each lot
is information from this derivation and reads differently at the next density
without anything having gone wrong. Two selections are refused in words rather
than accepted and ignored: members that are not neighbours in the sale's order
(the engine keeps consecutive runs together, and reordering is not built), and a
lot already in a pin.

**The instrument has a writer.** `/api/actions` takes a batch of gestures from
one sitting — a session id and sequence the CLIENT owns, per `schema.ts` — and
the client sends one for every correction gesture, fire-and-forget with
`keepalive`. D9 is measurable from this commit.

**Found on the way, not fixed here:** the migration wrote the predecessor's 13
`lot_field_overrides` — human decisions — with `decided_by = null`, so in
production they read as proposals and the engine will not apply them. The data
fix is one `update` to the gate identity, and it is an operator's decision.

## 8e. Templates as data

ROADMAP D6, pulled forward because the owner asked for a tearsheet and a price
list, and because built as two screens they would have been the third and
fourth renderer by Christmas — the defect principle 6 exists to prevent. So
they are **templates**: declarations the one engine reads and the one renderer
paints. `src/lib/engine/templates.ts` holds the whole argument; this is the
summary.

**How much structure the engine keeps.** The engine keeps the *grammar* and the
template supplies the *words*. The engine keeps pagination (file order, chunked
by density, a pin never split — the one algorithm the pin and override
contracts are keyed against), the *entry* (a lot on a page is a reference, a
plate and lines of field-and-value, in every output), and a **closed set of
three arrangements** — a grid of cells, a table of rows under a header, a sheet
that is a page — which the renderer knows the way HTML knows a table from a
list. The template declares the arrangement, the page (size, orientation,
margin), the type size, the **densities it offers with their budgets** — every
number that used to be a constant in the engine or the renderer — the plate's
placement and share, and the fields: print order, survival priority, table
width, and whether the label prints. `*` stands for the house's own columns; a
template without it prints only what it names.

**Three built-ins that are three shapes, not three sets of numbers.** The
catalogue is what rendered before, byte for byte (verified by diffing the old
renderer's markup against the new across every parameter). The price list is a
`<table>`: its columns are decided once for the document, so a lot with no
maker has an empty maker cell rather than its estimate sliding left. The
tearsheet is a `<dl>` on a page: the plate dominant, the specifications
labelled, and the budgets wide enough that the description prints whole.

**One renderer, still.** Two switches — how a page wraps its entries and how an
entry wraps its three parts — are the whole difference between the shapes,
inside one function with one stylesheet. A fourth shape is a fourth case of
those switches, not a screen. `test/templates.test.ts` holds the file to one
exported painter.

**No table, on purpose.** DFD.md §2. Nobody authors a template inside the
system yet, so the built-ins are validated constants and
`catalogues.params.template` names one by id — a row written before this
existed has no such key and is a catalogue, without a migration. The shape is
open for the first writer: `templateSchema` is the gate a stored jsonb row or an
AI proposal passes through, `derive()` takes the library of templates as an
argument, and the id is a string rather than an enum.

*Rejected:* more knobs on the grid (cannot say "table"); a box-geometry
language (Canva-shaped, and placing text in boxes means measuring text, which
is reading rendered output); templates that carry markup or CSS (a second
renderer by another name, and a script vector into a frame that is inert only
because its CSP has no script-src); template-declared pagination (would orphan
pins); one schema per arrangement (three vocabularies to learn and to
generate).

*Not done, and named:* a density chosen on one template is not remembered when
switching to another and back — the stored parameter is one number, and it
falls to the new template's default. Visible, adjustable, reversible; not
remembered. And the `/exports` ledger does not yet say which template each
sale's catalogue is on; the file name does.

## 9. Verification

`ARCHITECTURE.md` principle 10: measure, don't assert. Roughly two dozen defects
in the predecessor were found by driving the application and none by its suite.

- **Unit** — the engine, the mapping, the parser: pure functions, real fixtures.
- **Database** — against a real Postgres, never self-skipping.
- **Driven** — Playwright walks the six steps of §1 against the built
  application and **captures a screenshot at each**, which is the artefact that
  says the UI exists rather than that its tests pass.
- **The CSP control** — a script is injected into the preview frame and asserted
  *not* to run. This is the check principle 8 was bought with; it runs on every
  build, not once.
